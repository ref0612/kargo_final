Executive summary

KARGO coordinates freight between a client's own warehouses. A Merchant creates an order; a Logistics Coordinator assigns it to a Transport Operator, which collects, consolidates, line-hauls by intercity bus and delivers to the destination warehouse.

The business model

  • B2B only, warehouse to warehouse, one client account per relationship.
  • No payment at order creation. Billing is consolidated monthly per client.
  • ON HOLD The billing calculation basis has not been communicated yet and is parked to the end of the project.

The core design idea

  • Every physical hand-over of a package is a control point.
  • Each control point records who, when (date + time) and a scan of every package.
  • Pickup and final delivery additionally capture an electronic signature from a pre-registered authorized person.

Scope of the first release

  • Merchant creates orders and tracks them (read-only) — from a phone.
  • Coordinator assigns; operator crews execute with a mobile scanning app.
  • Backend is simulated with static JSON files for the prototype.

How the two reference apps informed this

  • kargo-flow-2: strong visuals, working mobile order form, but no package data.
  • kargo 2.0: strong process vision (multi-role, per-package manifest, event feed) but a demo simulation, not mobile-usable.
  • Decision: rebuild, combining the best of both.

Design rules that govern every screen

  1. The Merchant only creates orders. It never assigns carriers, scans, or manages operations.
  2. Mobile first — every role must be able to work from a phone.
  3. Every hand-over: scan of each package + timestamp + responsible user, with no exceptions.
  4. Identity verification is visual only: the Merchant registers at least two authorized persons per handover point (name, RUT, phone); the operator compares the RUT with the physical ID.
  5. Registration must take the fewest possible taps — it is the highest-frequency action in the system.

Merchant-facing status is intentionally simplified: Created → Assigned → Pickup in progress → In transit → Delivered. The eight internal steps (next section) exist in the back office and in the operator app only.

What each level is not allowed to do

  • Merchant cannot assign an operator, scan packages, or edit operational data.
  • Operator crews cannot create or modify the order's commercial data (warehouses, package declaration).
  • No role can alter a timestamp or delete a scan; corrections are new, attributed events.

Metrics that this design makes computable for free

Because every hand-over is timestamped and attributed, the following can be derived without extra data capture. These are candidate indicators offered for the consultant to confirm or replace:

Time-based

  • Creation → assignment (coordinator responsiveness)
  • Assignment → pickup (operator lead time)
  • Dwell time at operator WH1 (step 5 → step 7)
  • End-to-end lead time vs. SLA

Integrity-based

  • Scan completeness per control point (packages scanned ÷ packages declared)
  • Partial delivery rate and where the gap first appears
  • Handovers by person / crew (accountability)
  • Forced-manual registrations vs. real scans
05

Merchant order registration flow

A three-step, phone-first wizard. The Merchant's work ends at confirmation; everything in section 3 happens afterwards.

Rules that shape the flow

  • No scan or photo is required from the Merchant. The mandatory scans (and signature) are performed later by operator crews at each hand-over.
  • The only identity check is visual. The Merchant supplies the authorized persons; the crew member checks the physical ID against the RUT on screen.
  • Warehouses are registered once per Merchant account and reused. Most clients will have a single warehouse, in which case origin selection disappears; the model supports many, filtered by city.
  • High-volume path: Create → Bulk upload (CSV template, origin fixed per account, row-level error preview before confirmation).
  • No payment step. Billing is monthly and consolidated.

06

Data model

Design choices worth reviewing

  • The order timeline and each package's scan history are derived views of an append-only event log.
  • State is never overwritten; corrections are new attributed events.

Why per-package identity

  • An order can contain 1 to 40+ packages.
  • Scanning each one makes "which package is missing, and where did it disappear?" answerable from data.

08

Questions for the logistics consultant

The digital flow is specified. These seven points depend on operational experience, and each one changes what the software must do.

Failed or impossible scans. What is the accepted procedure when there is no signal, the label is damaged or the device fails? Proposal on the table: a manual forced registration with a mandatory reason code, flagged for review. Is that acceptable, and who reviews it?
Partial deliveries. If 24 of 25 packages are scanned at destination, when is an order "closed", who is notified, and how does it affect the SLA clock? Determines the incident workflow and the closure rule for step 8.
Label production. Portable thermal printer at the client's warehouse, or labels printed in an office beforehand? Affects hardware budget and how quickly a package can be tied to its order.
Authorized persons. Closed list per warehouse or free entry per order? How many are really needed for a warehouse that is staffed by one person? Two persons minimum is the current rule; it is the only identity control in the system.
Operator model. Does one Transport Operator serve several clients, or are operators dedicated? Can the Coordinator re-assign an order after pickup? Changes operator modeling and whether operators need their own coordinator view.
Service levels. Which SLA targets apply per route and per service type (standard / express), and where does the clock start and stop? The timestamps to compute it already exist; the targets do not.
Returns and damaged goods. What evidence (photos at each scan?), what liability boundary between operator and client, and what return flow? Photo capture is currently only implied at scan time; it may need to be explicit at every control point.
Deliberately out of scope for this review: billing. The monthly consolidated invoice exists in the model as an empty placeholder, and its calculation basis (per package, per order, per weight or fixed contract rate) is pending information from the business. It will be designed last and does not block any other phase.
